# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm start                        # run gateway via tsx (src/index.ts)
npm run dev                      # tsx watch
npm test                         # vitest run (single pass)
npm run test:watch               # vitest watch
npx vitest run test/unit.test.ts # run a single test file
npx vitest run -t "splitMessage" # run tests matching a name
npm run typecheck                # tsc --noEmit (must stay clean)
```

Tests write under `$HOME` (`~/.roundhouse`, `~/.pi/agent`, `~/.mcporter`). On a machine that runs roundhouse, run them with a throwaway home: `HOME=$(mktemp -d) npm test`.

There is no lint script. TypeScript is executed directly via `tsx`; `tsc` only typechecks and is never invoked at build/runtime. The only "build" happens implicitly when `roundhouse run` prefers a compiled `src/dist/index.js` if present; otherwise it imports `src/index.ts` into its own process (tsx is registered by `bin/roundhouse.mjs`).

Git hooks are installed by husky (`prepare: husky || true`, so `core.hooksPath` is `.husky/_`). `.husky/pre-commit` runs `scripts/scan-staged-secrets.sh` (secretlint over the staged blobs, config `.secretlintrc.json`) and then `.githooks/pre-commit` (pattern scan of added lines: Telegram/Anthropic/OpenAI/AWS/NPM). CI's `secret-scan` job runs a pinned, checksum-verified gitleaks over the full history; verified false positives go in `.gitleaksignore` by fingerprint. Don't bypass with `--no-verify` unless the user asks.

## Architecture

Roundhouse is a chat-gateway between chat platforms (via Vercel Chat SDK) and a **single** AI agent backend. Read `architecture.md` for diagrams; the points below are what's not obvious from the code.

**One gateway = one agent target.** Selection happens at startup from `config.agent.type` via `src/agents/registry.ts`. The `AgentRouter` seam (`src/router.ts`) currently always returns that one agent (`SingleAgentRouter`), but the interface is there so per-thread/multi-agent routing can be added without touching `gateway.ts` or the adapters.

**Streaming path vs. fallback path.** `Gateway.handleStreaming` (`src/gateway/gateway.ts`) prefers `agent.promptStream()` if the adapter implements it. It turns pi's event stream into Chat SDK calls:
- `text_delta` → buffered into a per-turn `AsyncIterable<string>` passed to `thread.handleStream()` (which does post+edit with rate limiting)
- `tool_start` → a compact status message via `thread.post()` (separate bubble)
- `custom_message` → flush the current streaming turn, post as its own bubble (used by pi extensions like pi-lgtm code review)
- `turn_end` / `agent_end` → flush so the next turn starts a fresh message
If `promptStream` is missing, `agent.prompt()` is called and the full text is split/posted via `postWithFallback` (markdown-first, plaintext fallback).

**Telegram answers are sent by roundhouse, not by the Chat SDK** (`src/transports/telegram/html.ts` and `format.ts`; the SDK's posting uses Telegram's legacy Markdown mode). What holds there:
- **Nothing is truncated.** A long answer is cut in its markdown source (`splitMarkdownForTelegram`, `takeMarkdownChunk`) so that each chunk's HTML fits one message; a code block or table that spans chunks is reopened in the next one. `scanLines` is the one place that decides where code blocks and tables are, and the converter and the splitter both read it. No chunk is without visible text: Telegram refuses an empty message, and the refusal sends the plain-text fallback, which shows raw fences.
- **Telegram is never called inside a wait it asked for** (`RateLimiter`). A 429 is waited out, up to `MAX_RATE_LIMIT_WAIT_MS` per answer; a wait longer than what is left is not started and the loss is logged. Sends and edits have separate waits, because Telegram refuses edits of one message for minutes while it still takes a new message. After a chunk that is held back, later chunks are not sent.
- **Streaming** edits one message at most every `STREAM_EDIT_INTERVAL_MS` (longer in groups). An edit in the middle may be skipped; a timer makes up for it when the stream goes quiet (a tool is running). The last edit of a message must arrive: if it cannot, the text the message does not show is posted as a new message.
- **The fake in `test/telegram-test-helpers.ts` refuses what Telegram refuses** (empty text, HTML it cannot parse, more than 4096 visible characters, an edit that changes nothing). Keep it that strict: a lenient fake is how an empty code block and raw table rows got through. The generated-document tests are seeded; a failure names the seed.

**Pi adapter nuance — wait for idle, not for `prompt()`.** `src/agents/pi/pi-adapter.ts` targets pi 1.x (`@earendil-works/pi-coding-agent`, pinned to the exact version in `package.json`). Since pi 1.0, `session.prompt()` resolves only after the run has settled: retries, compaction, follow-ups queued by `agent_end` handlers and the `agent_settled` handlers are all inside it. A run an extension starts *after* that (`pi.sendMessage(..., { triggerTurn: true })` while idle) is not, so `runPromptAndFollowUps` then loops on the public `session.isIdle` / `session.waitForIdle()` before the caller unsubscribes. Unsubscribe earlier and Telegram shows a review bubble followed by silence. Do not reintroduce the pre-1.0 workarounds (awaiting the private `_agentEventQueue`, calling `agent.continue()` by hand): that field is gone and the session drains its own queues.

**Pi adapter nuance — "still working" notices come from events.** `promptStream` emits `draining` when a new low-level run (`agent_start`) begins after one already ended (`agent_end` with `willRetry: false`) inside the same prompt, and `drain_complete` on `agent_settled`. A retry is not a new run for this purpose.

**Pi adapter nuance — models and auth.** One lazily created `ModelRuntime` (pi's replacement for `AuthStorage` + `ModelRegistry`) is shared by all sessions. Per-call model overrides (`promptWithModel`, `compactWithModel`) swap `session.agent.state.model` in memory and restore it; they deliberately avoid `session.setModel()`, which writes a model change into the transcript.

**Pi adapter nuance — errors are reported when pi has not recovered.** A failed assistant message is held, not emitted: pi retries transient errors (`auto_retry_start` clears it) and compacts-and-retries on overflow. For overflow the error stays held until `compaction_end` says the retry is on (`willRetry`, no `errorMessage`); a failed summary ends the run with no new assistant message, and the held overflow is then what starts roundhouse's own recovery. The held error is emitted as `model_error` when a follow-up run starts (so a successful follow-up cannot bury the owner's failed request) or at `agent_settled`. Only pi's own retry and its retry after an overflow compaction are exempt from the `draining` notice; a run after a threshold compaction is queued follow-up work. `test/pi-adapter-stream.test.ts` scripts these sequences against a fake SDK.

**Standing context lives in the system prompt (pi).** `src/index.ts` hands the adapter `standingContext: buildStandingContext` (persona + `tools.md`, `src/gateway/standing-context.ts`). The pi adapter builds the same `DefaultResourceLoader` pi would, with that text appended to the system prompt, and reports `getInfo().standingContext === "system-prompt"`; the gateway then skips the per-message `<persona>`/`<tools>` blocks. Before each prompt the adapter compares the text and calls `session.reload()` if it changed. Adapters that ignore the option (kiro) keep the per-message copy. Adapters created without it (cron runner, `roundhouse agent`) get no persona, as before.

**Compaction thresholds follow the model.** `contextThresholds()` in `src/memory/policy.ts` turns the model's context window into soft/hard token thresholds (fractions of the window, optional absolute caps, per-model overrides under `memory.compact.models`, never above `window - COMPACT_HEADROOM_TOKENS`). Do not reintroduce absolute defaults: they made a 1M-window model compact at 15%. The flush model is opt-in, and `fitsModel()` in the pi adapter skips it when the conversation exceeds its window.

**One gateway per home directory, and a stop always ends the process.** `src/instance-lock.ts` holds `~/.roundhouse/gateway.lock` (pid + start marker + running/stopping). The lock is created by hard-linking a complete file into place and a stale one is removed under a second claim file, so simultaneous starters cannot both win (`test/instance-lock.test.ts` races six real processes); keep those two properties if you touch it. `roundhouse run` runs the gateway in its own process (no child), `index.ts` marks the lock "stopping" on SIGTERM/SIGINT and force-exits after 20 s, and `Gateway.stop()` sets `stopping` (no new turn, flush or compaction starts), aborts turns, and bounds every step; the pi adapter refuses to open sessions after `dispose()`. A successor waits for a stopping holder and kills it if it lingers; it refuses to start next to a running one. The failure this prevents: an old gateway finishing a long turn after its service was restarted, with two processes polling the same bot and forking the session file.

**Handlers return at once; the turn runs detached.** The Chat SDK's Telegram polling awaits a message handler before it asks for more updates. A handler that awaited the agent turn made the bot deaf for the length of the turn (`/cancel` could not arrive). `accept()` in `Gateway.start()` starts the work and returns; `inFlightWork` tracks it and `whenIdle()` waits for it (tests use that). Messages are chained per chat in arrival order, because `handle()` awaits pairing and attachment downloads before the turn lock. Only commands about the running turn or the gateway skip the chain: the pre-turn ones and descriptors marked `immediate` (`skipsTheLine`). `/new`, `/topic`, `/compact` and commands the gateway does not know (prompts for the agent) stay in line; letting them jump moved earlier messages into the wrong conversation. Button handlers (`onAction`) are detached the same way. `test/telegram-slash-integration.test.ts` drives the adapter's real polling loop and fails if a handler blocks again. Consequence: Telegram considers a message delivered before its turn ends, so a turn cut off by a restart is not redelivered. `accept()` therefore writes a marker in `~/.roundhouse/in-flight/` for every allowed request, removed when its work ends, so it survives only a request that was cut off or never started. The next gateway reads the markers before `chat.initialize()` (a message waiting at Telegram starts its turn, and writes its own marker, the moment polling begins) and reports that snapshot, one notice per chat, instead of re-running anything. `Gateway.stop()` stops polling first for the same reason. `/cancel` acts on `runningTurns` (keyed by chat, set when the turn is accepted), not on the session the chat currently points at.

**`/stop` is `/cancel` plus a review, and the review is read-only.** `handleStop` (`src/gateway/stop-command.ts`) is a pre-turn command: it takes a snapshot of the turn (`describeTurn()`; pi: `renderTurn()` over `session.messages`, which must not go through the thread queue because the turn holds it), aborts the running turn exactly as `/cancel` does, sets the agent's note (`StopNotes.stop`) *in the same tick as the abort* so the next queued message cannot slip past its check, then spawns a `review` sub-agent with `tools: ["read","grep","find","ls"]` (the launcher adds `--no-mcp --no-context-files --no-prompt-templates --no-themes --no-approve`: `--tools` alone keeps MCP tools, and the working directory's `AGENTS.md` is text the stopped agent could have written), `delivery: "chat"`, and the turn as `turn.md` in the run folder (`SpawnSpec.files`). A turn whose abort signal is already set (stopped or cancelled a moment ago, still winding down) is not noted or reviewed again, but `agent.abort` is still called: after an abort the turn can be saving memory or compacting, and the first abort may not have taken. It reviews the snapshot taken before the abort when a later request has begun by the time the abort settles; it does not review at all when the turn's request is not in the conversation yet (`running.started` false, or `TurnDescription.reached === false`: the pi adapter stamps `promptStartedAt` when a prompt leaves its queue and compares the last user message's timestamp with it), because the last user message is then an earlier turn; two snapshots are told apart by `requestAt`, not by the words of the request. (The adapter's mark is `promptAskedAt`, set when `promptStream`'s iterator starts, not when the prompt leaves the thread queue: a turn queued behind a memory save has not begun either.) In `renderTurn` a turn starts at the last user message that is not the gateway's memory-save prompt (`MAINTENANCE_PROMPT_RE`; a test holds it to `buildFlushPrompt`), falls back to the last `compactionSummary` when the request was compacted away (`requestAt` is then the summary's time), and is preceded by the exchange before it (`contextBefore`: the previous owner message and the end of the assistant's last reply), which is context for the reviewer and never counted as steps. Keep the reviewer without a shell: the transcript is untrusted text. `renderTurn` puts every line of request, speech, call arguments and results behind `│ `, removes obvious secrets (`redactSecrets`, best effort), and marks a call with no result. `handleSubagentCompletion` sends a `delivery: "chat"` run to `deliverReviewToChat` (redact, post, delete `turn.md`, hand the report to `StopNotes.report`) instead of `injectSubagentResult`; the delivery is stored in `status.json`, so a restart between spawn and completion still posts. `StopNotes` (in memory; a list of records per session, one per stop, each with its own review, at most `MAX_ACTIVE_REVIEWS` running) gives each stop note once and each report once: `peek()` in `handleAgentTurn` after the checks that can drop the turn and after transcription, `commit()` only when the prompt starts, so a message dropped in between leaves the note for the next one; `pending` keeps a record alive while `/stop` is still starting the reviewer; a report is matched to its stop by run id (so two reviews can finish in either order, and the post's title carries the stop's time), and the report text has `<` `>` replaced so it cannot close its `<stop_review>` wrapper. `SubAgentOrchestratorImpl.spawn` arms a deadline timer: the watcher skips runs the same process started, so nothing else enforces it. `test/stop-review.test.ts` drives the gateway with a fake agent and sub-agent service.

**Commands that change the conversation go through the adapter.** `/new` calls `restart()`, which leaves a `.new-session` marker in the thread's session directory; `createSession` then uses `SessionManager.create` instead of `continueRecent` (which reopens the newest transcript, i.e. the one just closed) and records the fresh session's file name in the marker. The marker goes once a prompt in that session completes, or at the next `createSession` if the named file exists (pi writes the transcript as soon as the first message is appended, so a restart in the middle of the first turn resumes that session instead of starting a third). `/model` writes pi's default and calls `setModel()`, which uses `session.setModel()` on purpose: pi restores a session's model from its transcript, so the default alone never reaches an existing conversation. (The temporary flush/compaction swaps still avoid `setModel()`.) `/think` uses `thinkingLevel()`.

**An abort also cancels what has not started.** `session.abort()` stops what is running; a streamed prompt that is still waiting in the thread queue (behind a memory save), opening its session or loading images is not running yet, and used to start afterwards and run in full with nobody reading. `promptStream` takes a number from a counter when it is called, `abort()` records a later one for the thread before anything else, and `runPromptAndFollowUps` returns without calling `session.prompt` when the abort is the later of the two (`test/pi-adapter-session.test.ts`). A run that begins after such an abort all the same (pi's `abort()` only reaches a run that is under way, not one still in `prompt()`'s preflight) is aborted again at its `agent_start`. The non-streamed path (`doPrompt`: memory flush, cron) is not covered, on purpose: a skipped flush would be recorded as done. The adapter also tells the gateway when the agent really has a message (`PromptHooks.onStart`, `AdapterInfo.reportsPromptStart`); until then what the message carries counts as undelivered: the `/stop` note is committed on it, and a memory injection is re-armed (`rearmMemoryInjection`) when the turn ends without it. In the gateway, `runningTurns` holds a turn from the moment it is accepted only if the chat has no record; a turn that arrives while another holds the place (a sub-agent's result during the owner's turn, or his message during the result's) registers when it gets the thread lock, so `/cancel` and `/stop` always act on the turn that is running.

**Thread serialization.** The pi adapter keeps one queue per `threadId` (`threadQueues` in pi.ts). `prompt()` and `promptStream()` both `enqueue()` onto this chain so overlapping user messages in the same thread never race inside the pi session. Don't remove this — pi sessions are not safe for concurrent prompts.

**Per-thread sessions persist as `.jsonl`** at `<sessionDir>/<threadIdToDir(threadId)>/<session>.jsonl` (default `~/.roundhouse/sessions/`). Thread IDs are encoded reversibly by `threadIdToDir` in `src/util.ts` (`_` → `__`, `:` → `_c`, other → `_xNNNN`) so that `telegram:123` and `telegram_123` do not collide. `SessionManager.continueRecent` resumes the most recent jsonl in that dir; `SessionManager.create` starts a new one if none exist.

**Config resolution order** (src/config.ts → `loadConfig`): `ROUNDHOUSE_CONFIG` env → `--config <path>` CLI flag → `~/.roundhouse/gateway.config.json` (with legacy fallback to `~/.config/roundhouse/`) → `./gateway.config.json` → `DEFAULT_CONFIG`. Then `applyEnvOverrides` layers `BOT_USERNAME`, `ALLOWED_USERS`, `NOTIFY_CHAT_IDS` on top. Secrets (`TELEGRAM_BOT_TOKEN`, `ANTHROPIC_API_KEY`) are always env-only, never read from config.

**Who may drive the agent** (`isAllowed` in `src/util.ts`; wired in `Gateway.start()`). Anyone whose message is accepted gets the agent's shell, so this is the security boundary:
- `chat.allowedUserIds` non-empty: only those immutable platform ids pass, and usernames are ignored. Pairing fills this list.
- Otherwise `chat.allowedUsers`: matched against `verifiedHandle()`, never against the Chat SDK's `author.userName`. On Telegram the SDK builds `userName` as `from.username ?? from.first_name ?? id`, so an account without an @username can set its first name to the owner's handle; only `raw.from.username` counts. On Slack `userName` is the display name, so `verifiedHandle()` returns nothing there and Slack users authorize by id only. Slack pairing (`src/transports/slack/pairing.ts`) still matches the display name and has no one-time code.
- Both empty: everyone is refused unless `chat.allowAll: true`.
- The check runs before `thread.subscribe()`, before the message is logged, and on inline-button presses (`chat.onAction`). `chat.dmOnly: true` ignores groups, channels and topics (`isPrivateChat` in `src/gateway/helpers.ts`). Keep new handlers behind the same `allowed()` helper; `test/security-hardening.test.ts` covers the wiring.
- **Four entry points, one path.** The Telegram adapter does not pass a message that starts with a bot command (`/status`, `/cancel`, `/start <code>`) to `onDirectMessage` / `onNewMention` / `onSubscribedMessage`; it raises `onSlashCommand`. The gateway rebuilds the message there and sends it through `handleOrAbort` like the other three. `test/telegram-slash-integration.test.ts` feeds raw updates through the real adapter; use it when bumping the Chat SDK, since a routing change upstream shows up as commands that silently do nothing.

**Install/daemon.** `roundhouse install` writes `~/.roundhouse/gateway.config.json`, an env file at `~/.roundhouse/.env` (merged with existing so manually-added keys survive), and a systemd unit that uses `roundhouse run` (foreground mode) as ExecStart. `roundhouse start` starts the daemon via systemctl; `roundhouse run` runs in the foreground (used by systemd and for dev). `roundhouse update` does `npm update -g` then `systemctl restart`. All chat input in the daemon goes through the unit's `EnvironmentFile`.

**Adding a new agent backend:** implement `AgentAdapter` from `src/types.ts` in `src/agents/<name>.ts`, register in `src/agents/registry.ts`, set `"agent": { "type": "<name>" }` in config. If you want streaming, implement `promptStream` yielding `AgentStreamEvent`s; otherwise `prompt` alone is enough and the gateway will fall back.

**Adding a new chat platform:** install the `@chat-adapter/<platform>` package, register it in `chatAdapterFactories` (`src/transports/chat-adapters.ts`), implement a `TransportAdapter` (`src/transports/<name>/<name>-adapter.ts`), add it to `buildTransportDelegates` in `src/gateway/gateway.ts`, and add a corresponding entry to `GatewayConfig["chat"]["adapters"]` in `src/types.ts`. The composite transport routes all per-thread methods automatically by `ownsThread`/`ownsChatId`.

**Multi-transport composition.** A single gateway runs all configured transports simultaneously through `CompositeTransportAdapter` (`src/transports/composite.ts`). The composite owns a `delegates: TransportAdapter[]` and routes:
- per-thread methods (`postMessage`, `postRich`, `progress`, `stream`, `enrichPrompt`) by the first delegate where `ownsThread(thread)` is true;
- `notify(chatIds, ...)` by partitioning chat ids by `ownsChatId` then fanning out;
- `handlePairing` to the first delegate that returns non-null, decorated with `transport: <delegateName>` so the gateway tracks `pairingComplete` per-transport (a `Map<string, boolean>` — a single boolean would silently block the second transport's pairing once the first paired);
- `registerCommands` and `dispose` to all delegates.
The gateway never branches on platform; everything reads `this.transport.foo()` against the composite.

**Slack adapter nuances.**
- Thread ids are `slack:CHANNEL:THREAD_TS`. Always use `sdk.encodeThreadId({ channel, threadTs })` and `sdk.decodeThreadId(id)` — never split manually. Top-level posts use `threadTs: ""` (sentinel); the `progress.ts` and `streaming.ts` helpers check for `"" | "main"` and elide `thread_ts` when posting.
- `AdapterPostableMessage` is `string | { raw } | { markdown } | { ast } | { card } | CardElement` (`chat@4.29.0` `chat-D9UYaaNO.d.ts:1549`). **There is no `blocks` field.** Menus go through `{ card, fallbackText }` and the SDK's `cardToBlockKit` does the conversion internally. Same model works for telegram via `extractCard`. The transport-agnostic `richMenuToCard` lives in `src/transports/rich-helpers.ts` and is shared.
- **Streaming + Block Kit can't coexist.** Slack's stream API doesn't take blocks. Decision: streaming turns are agent text only; menu turns are command results that don't stream. If a future feature needs both, finalize the stream first then post a separate menu message.
- **`SlackAdapter.attach(slackSdk)` lifecycle.** Must be called *after* `chat.initialize()` because the Chat SDK Slack adapter populates `_botUserId` and starts socket-mode during initialize. The gateway does this for you (`gateway.ts` post-`chat.initialize()` block); don't call `attach()` earlier or webClient calls will throw `AuthenticationError`.
- **Bot self-loop filtering.** Slack delivers the bot's own messages back through `message.channels` / `message.groups` if those scopes are enabled. The Chat SDK does central isMe filtering; verified that the SDK's `initialize()` already calls `auth.test` and populates `_botUserId` before subscriptions activate (`@chat-adapter/slack@4.29.0` `index.js:868-885`), so the filter is armed by the time events flow.
- **Pairing chicken-and-egg.** Slack's `message.im` only fires for *existing* DM channels. To support users who haven't DM'd the bot yet, the gateway also registers `bot.onAssistantThreadStarted` and synthesizes an IncomingMessage from the event (resolving the user via `slackSdk.getUser(userId)` so the allowlist's userName check has a value to match). Both paths flow through the same `transport.handlePairing` → composite seam.
- **Per-transport boot turn.** `fireBootTurn` partitions `notifyChatIds` by `ownsChatId` and fires one boot turn against the first chatId owned by each transport — not the global `chatIds[0]`. Otherwise multi-transport installs would silently favor whichever transport happened to be listed first.
- `createSlackAdapter` env-var fallback only fires when called with NO config (`zeroConfig = !config`). The factory in `src/transports/chat-adapters.ts` therefore explicitly forwards `process.env.SLACK_BOT_TOKEN` / `SLACK_APP_TOKEN` / `SLACK_SIGNING_SECRET` so they're populated regardless of whether other config keys are set. Verified against `dist/index.js:4233-4243`. Skipping this is a silent `AuthenticationError: No bot token available` at runtime.

**Type widening for multi-transport.** `allowedUserIds` and `notifyChatIds` are `(string | number)[]` (Telegram numeric, Slack string). `ChatThread.post` accepts `string | { markdown } | { card, fallbackText? }`. `IncomingMessage.chatId` is `string | number`. `isAllowed` does dual lookup against the heterogeneous union by normalizing both sides to `String()`. Several legacy `Number()` coercion sites were caught in Phase 1 (`gateway.ts:113, 329, 352, 978-1001, 1017-1021`, `subagent-command.ts`, `ipc/handler.ts`) — preserve string IDs end-to-end; don't reintroduce `parseInt` or `Number()` casts.

## Debugging

Set `ROUNDHOUSE_DEBUG_STREAM=1` to log every stream event in `gateway.ts` (`[roundhouse/stream]`) and every pi session event in `pi.ts` (`[pi-agent/sub]`). Evaluated once at module load (`DEBUG_STREAM` in `src/util.ts`), so toggling requires a restart.
